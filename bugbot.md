# Bugbot

Project-specific review rules for `panenco/claude-review` itself. This repo IS
the upstream review pipeline, so most findings concern the pipeline's own code,
prompts, and config — not an application.

## What this repo ships

- Bash scripts under `scripts/` (review plan, token picker, review posting, dev-env setup, usage tooling).
- Skill prompts under `skills/review-*.md` — read verbatim by Claude in CI.
- Reusable workflow `.github/workflows/pr-review.yml` (`workflow_call`).
- Composite action `action.yml` that installs skills/scripts into the consumer workspace.
- Setup recipe `prompts/setup-review.md` — read verbatim by Claude when a user runs `/setup-review`.

## Rules

- **Skill prompts and the setup recipe are executable assets, not prose.** Files in `skills/` and `prompts/setup-review.md` are read verbatim by Claude at runtime. Wording, heading levels, and exact strings (e.g. `### Auth`, `### Known service ports`, `Sign in:`, `Method: cookie|bearer|header|none`) are load-bearing — `pr-review.yml`'s validate step greps for them literally. Edit like code: any change risks shifting verdicts or breaking auto-extraction.
- **Shell scripts use `set -uo pipefail` only — never add `set -e`.** Documented rationale lives in `prompts/setup-review.md` (Step 4.5): `set -e` produces surprising failures in idioms like `curl || true` and `grep` pipes that legitimately return 1. Explicit `exit N` on every error path is the contract.
- **Readiness loops must fail fast.** Any `for i in $(seq …); do …; break; done` that probes a service must be followed by an explicit `if [ "$READY" != "true" ]; then echo ::error:: …; exit 1; fi`. Silent-success-on-timeout is the #1 bug we flag in consumer review-configs — don't ship it in our own examples or scripts.
- **Pipeline-ref alignment is required for non-`@v3` consumers.** GitHub does not expose the called workflow's resolved ref to the called workflow itself, so `pr-review.yml` accepts `pipeline_ref` (default `'v3'`) and the install step checks out `panenco/claude-review` at that ref. Consumers pinning the workflow file at a non-default ref (a SHA, a feature branch) MUST also pass `with: pipeline_ref: <same-ref>`; otherwise the workflow runs new orchestration with old skills and the build-context agent hits max-turns. Preserve this note when editing tag/release guidance.
- **`anthropics/claude-code-action` restores `.claude/` from `origin/main` for untrusted PR heads.** Anything we write under `.claude/skills/` in the workspace is wiped at agent-launch time. The current install pattern (export `CLAUDE_REVIEW_PIPELINE_DIR` to the action's own download path, copy scripts to `.review-scripts/` which is *not* on the restore list) exists for this reason. Don't "simplify" by moving skills into the workspace.
- **Pipeline changes need an end-to-end thought, not just a code review.** A change to `post-review.sh`, any `skills/review-*.md`, any `agents/review-*.md`, or `pr-review.yml` can break every consumer repo on the next PR push (we ship `@v3` as a moving tag). Verdict-affecting changes especially: trace what flows into `/tmp/review.json` and `post-review.sh` before approving.

## Verify before flagging

Before reporting a finding that cites a file, capability, or string, confirm it exists:

- Repo capabilities live at `scripts/`, `skills/`, `prompts/`, `.github/workflows/pr-review.yml`, and `action.yml`. Anything outside that surface is unlikely to be present.
- The runtime-generated `context.md` is not committed; references to "context.md" inside skills are deliberate (they describe the file the Context Builder writes during a review run, not a checked-in file).
- If unsure whether an artifact exists, drop the finding or move it to `uncertain_observations`.

## Accepted supply-chain trade-offs

- The caller workflow `.github/workflows/claude-review.yml` calls the reusable workflow via the **local path** `./.github/workflows/pr-review.yml`, not the cross-repo form `panenco/claude-review/.github/workflows/pr-review.yml@v3` that consumers use. It also pins `pipeline_ref` to the PR's head SHA (`github.event.pull_request.head.sha || github.sha`) so skills + scripts come from the same commit as the orchestration, not from `@v3`. Reason: the `org/repo/...@tag` form tripped `startup_failure` on this repo even with explicit secret mappings (documented quirk in `prompts/setup-review.md` Step 2), and pinning to head.sha makes script-level changes visible on their own PR — without the pin, only orchestration changes get dogfooded in-PR while every other change has to be merged before it's exercised. Do not flag either divergence as "diverging from the documented Quick Start"; both are intentional and documented in the workflow's inline comment.
- The reusable workflow's downstream install step checks out `panenco/claude-review` at `inputs.pipeline_ref` (default `'v3'` — a moving tag). This is identical to the consumer-side guidance in the README and is explicitly accepted: do **not** flag the default `@v3` install as a security finding. The trade-off (mutable tag for fast propagation across consumer repos) is the same one the README declares.
- The review job's `plugin_marketplaces` input installs `https://github.com/anthropics/claude-plugins-public.git` at whatever its default branch points to — an unpinned live git ref, and the only third-party reference in `pr-review.yml` that is not SHA-pinned. **It cannot be pinned today**, verified against `anthropics/claude-code-action` at the pinned SHA `ac7e24bf`: `base-action/src/install-plugins.ts` validates the input with `MARKETPLACE_URL_REGEX = /^https:\/\/[...]+\.git$/`, whose `\.git$` anchor rejects `…public.git@<sha>`, `…public.git#<ref>` and `…public.git?ref=<ref>` outright; `addMarketplace()` then shells out to exactly `claude plugin marketplace add <url>` with no ref argument, and the action exposes no input for one. `claude plugin marketplace add --help` (CLI 2.1.234) offers only `--scope` and `--sparse` — no `--ref`/`--sha`. Claude Code's docs state that git-based *marketplace* sources support `ref` (branch/tag) but **not** `sha`, and only in the `extraKnownMarketplaces` object form in `settings.json`, which this input cannot express — and `claude-plugins-public` publishes no tags and no releases, so `ref` would only buy another moving pointer. Blast radius, restated for the in-session design (the separate `native-review` job was replaced by the in-session `review-native` subagent). Be precise about what constrains it, because the job itself is NOT read-only: it holds `contents: write`, `pull-requests: write` and `issues: write`, and the plugin's subagents inherit that token. Two things contain it. **(1) A session-wide deny list.** `--disallowedTools` on the `Review: orchestrate` step denies `Edit`, `WebFetch`, `WebSearch`, the raw `gh` API subcommand, every `gh pr` write verb (`comment`, `review`, `edit`, `close`, `merge`, `ready`), `gh issue comment/edit/close`, `gh release` and `git push`. Deny rules are evaluated before allow rules, `--permission-mode dontAsk` makes the list bind rather than merely auto-approve, and it binds every subagent the plugin fans out to — tool calls are authorised session-wide and an agent definition's `tools:` frontmatter can only narrow, never widen. What is left reachable is reads: `gh pr view/diff/list`, `gh issue view`, `gh search`, `git log/blame/diff/show`. **(2) All privileged API access lives in reviewed scripts.** The pipeline's own raw REST/GraphQL calls were extracted into `scripts/fetch-pr-threads.sh` (reads) and `scripts/upload-screenshots.sh` (the `review-assets` blob/tree/commit/ref writes), invoked as `.review-scripts/<name>.sh` — which is what makes denying the raw API verb possible at all, since `--disallowedTools` cannot be scoped to one subagent. Together these restore the read-only posture the deleted separate job had (`contents: read` plus a narrow allowlist), which is what made moving the plugin in-session safe. The one thing that reaches the PR is `/tmp/review.json`, written by the orchestrator and posted by `scripts/post-review.sh`; the plugin prompt cannot write it and cannot post around it. What remains is that an untrusted prompt is read into a session holding a Claude OAuth token and a repo-write token, over attacker-controlled PR content, contained by a deny list. This changes the day the action grows a ref/sha input or the marketplace starts tagging releases — then pin it in the usual house style. Until then, do **not** flag it, and do **not** propose a ref suffix: the action rejects one.
